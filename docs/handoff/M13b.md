# Handoff: M13b, tool groups, so Mary only holds the tools for what you're doing (second account, branch `other/M13b`)

Read `docs/handoff/_common.md` first (it sends you to `docs/mission.md`). Then read section 12 of `docs/skills-design.md`, `skills_core.py` (`gemini_tools` near line 893 and `instruction_text`), the tool lists in `mary.py` (near lines 518-705), `LIVE_TOOLS_NOTE` in `voices.py`, and how the page passes Live tool calls to `window.MarySkills` (`web/mary/app.js` near line 1750, and the skills script it loads).

**Why:** with word search, Mary holds 20 skill tools plus her own, about 26 in all. That's past the planned limit of about 20, and every new game adds more. Too many tools at once make a model pick the wrong one (a picture when you meant "show me the word") and slow it down.

**Andy's decision (2026-10-31):** "let's group her tools, so she only has access to a certain amount of tools for whatever thing you ask her about. If you ask her about the word search, she's not going to have access to the tools for pulling up a picture… little groups." The hub's call on how: **each skill is one group.** Skills are already the modules, so groups come free, and a new game brings its own group with no core change.

**Goal:**
1. **Always on hand:** her own tools (memory, story, end talk), one tool to open a group, and the tools of the active group: the skill on screen, or the one she opened last. A skill may mark a very small set as always on hand only when residents need it mid-anything, like louder and softer. Keep that rare, and say which you chose.
2. **The menu:** her instructions list every group in one line each (title and what it's for), so she knows what she can open.
3. **Switching:** when the talk turns to something else ("show me a picture of a cardinal" during word search), she opens that group in the same turn, without asking and without saying anything about tools. Opening a group by itself changes nothing on screen.
4. **One thing beside her at a time (Andy, 2026-10-31):** "she just hides the game for a minute and shows you the picture." When a second thing needs the screen, such as a picture during a game, the game is set aside exactly as it was, not ended, and the picture takes its place beside Mary the same way. When they're done with the picture, by voice ("back to the puzzle") or by closing the picture, the game comes back where they left off. She may mention it once in one line ("your puzzle's right where you left it"). No overlays, and no shrinking Mary into a corner to fit two things. Use the existing screens and controls; if a new button is needed, commit `WAITING` with what it would say.
5. **All three talk modes.** Normal and Offline can rebuild the tool list each turn. Live fixes its tools when the talk starts, so pick a pattern that works there too: for example, the open tool's answer carries the group's actions, and one generic tool runs them. Use one pattern everywhere if you can; if you use two, say why. Keep the Gemini 3 `thoughtSignature` handling working.
6. **Untouched:** emergency and crisis handling never depend on tools or groups; prove it with a test. The offline phrases with no Gemini keep working. `set_skill` keeps working.
7. **A ceiling:** however many skills are installed, she never holds more than about 12 tools at once. Test it with ten fake skills.

**Start only after `other/M7a` is merged into main** (the hub tells you). Stay out of files others are changing: M8's new module and its marked lines in `server.py`, and `tools/brain_bench.py`. Update `docs/skills-design.md` and the skills how-to to match.

**Tests** with fake Gemini: the group limit, switching groups, word search hiding the picture tools, a picture setting the game aside and the game coming back unchanged, the Live path, the open-tool answer, safety untouched, and offline phrases. Run `node --check` on changed scripts.

**Models:** Opus coder for the design and the core (xhigh), Sonnet coder for the tests, Haiku only for doc wording. Checkpoint after each piece passes.

**Finish:** commit `DONE: M13b tool groups` with a short report: the pattern you chose, the tool count before and after, and what isn't verified (real Gemini; the hub's bench run will check for wrong tool picks). If anything a resident would see or hear changes, commit `WAITING: …` instead. Then stop.
