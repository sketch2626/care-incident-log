# Handoff: M8, a first-run speed check that fits Mary to the laptop (second account, branch `other/M8`)

Read `docs/handoff/_common.md` first (it sends you to `docs/mission.md`). Then read only what you need from `speech.py` (the `WhisperModel` setup near line 128), `wakeword.py`, `voices.py` (Kokoro, near line 56 and 598-615), `desktop.py` (startup) and the M8 item in `docs/mary-roadmap.md`.

**Why (Andy, 2026-10-30):** many residents get new donated Lenovos like Andy's (Ryzen 5 7520U, the laptop you're on), and some get refurbished ones that are slower. Nobody should have to tune Mary by hand. A resident in her 80s must never wait in silence because her laptop is old.

**Goal:** on first run, Mary checks the laptop quietly and picks lighter settings by herself when it's slow.
1. **The check.** Time Kokoro's first spoken sentence, Whisper on a short fixed clip (make a small test clip with Kokoro or Windows' voice at build time, not a recording of anyone), and the wake word's steady CPU use. It runs in the background after her window is up. It never delays her first hello, and it's done in about 20 seconds.
2. **The tier.** From the timings, pick "normal" or "light" (a third tier only if the numbers show it's needed). Save the timings, the tier, the date, the CPU name and core count, and the app version in settings. Run the check again when the CPU or the app version changes. Add a way to run it again on request (an API route is enough, no new screen).
3. **What "light" changes.** Measure first, then choose only from settings the code already has or can change cheaply: Whisper threads, the wake word's confirm step, how much work starts at once, and similar. Anything a resident would see or hear differently, like a different voice, the computer voice, fewer animations or slower replies, is Andy's call. Build it behind a setting that's off, and commit WAITING with the choice.
4. **Thresholds.** Measure this laptop as the "new Lenovo" baseline. Then imitate a slow laptop by limiting threads or CPU affinity to two cores, and set thresholds between the two. Put the numbers in the report.

**Stay out of** files others are changing now: `mary.py`, `memory_core.py`, `tools/brain_bench.py`, `skills/word_search/`, `web/mary/app.js`. Keep changes to `server.py` small and marked `M8`. Put the new code in its own module.

**Tests** with fake timers and fake engines: tier picking, the re-check triggers, saved settings, and the check never blocking startup. Real timing runs only in a tool such as `tools/laptop_check.py`, never in the test suite. Use a scratch `APPDATA`, never the real data folder or Andy's key. No Gemini calls are needed.

**Not in scope:** the free-tier key check from `docs/companion-plan.md`, and the installer build.

**Models:** Opus coder for the new code (xhigh for the threading), Sonnet coder for the tests, Haiku only for doc wording. Checkpoint after each piece passes, as `_common.md` says.

**Finish:** commit `DONE: M8 laptop speed check` with a short report: the timing table (real laptop and imitated slow one), the thresholds, what "light" changes, and what isn't verified. Commit `WAITING: …` instead if a visible or audible change needs Andy. Then stop.
